workflow

spec → merge
the m3j workflow

A port of Chris Titus's AI coding workflow for OpenCode, free-tier models only. An idea becomes a reviewed, mergeable PR through small phases — each phase ships as one reviewable change.

the pipeline

ten steps to a mergeable PR

Working files — SPEC.md ROADMAP.md TASKS.md — live at the project root, seeded from templates/. A quick inventory first: create or refresh whatever's missing. Run the steps in order; each done-criterion must be met before the next starts.

01

SPEC

plan the contract

m3j-planner writes SPEC.md from template — problem, users, required behavior, architecture, security, pinned dependency versions, non-goals, acceptance criteria.

m3j-planner

02

ROADMAP

sequence the phases

m3j-planner writes ROADMAP.md from template — phases with checkable exit criteria and explicit dependencies, ≤3 tasks per phase.

m3j-planner

03

TASKS

slice vertically

m3j-planner writes TASKS.md from template — vertical slices, each delivering working value alone, with an acceptance command plus expected output and TDD checkbox steps.

m3j-planner

04

test scaffold

harness before features

m3j-tester sets up the harness — test runner, lint, format, typecheck — before any feature code exists. It must run green on an empty baseline.

m3j-tester

05

one phase

tdd, one phase per session

m3j-executor implements ONE phase from TASKS.md, TDD. One phase per session — never the whole roadmap in one context.

m3j-executor

06

/finish

local gate

m3j-sentinel runs the 7-step quality gate. All 7 steps report pass or fail — every failure is fixed and re-verified.

m3j-sentinel

07

one PR

small & reviewable

m3j-devops opens one small, reviewable PR containing only this phase's change, naming the phase and its acceptance criteria.

m3j-devops

08

fresh-context review

never grade your own work

A new m3j-triage or m3j-sentinel session — with no memory of the implementation — reviews the PR. Never the implementing session.

m3j-triage

09

fix / retest

verify before accepting

m3j-executor fixes each finding, then re-runs the acceptance commands and /finish. m3j-triage vets each suggestion for technical soundness first.

m3j-executor m3j-triage

10

human merge gate

nothing merges without you

Present the PR with the checklist — diff scope, tests + CI, review threads, docs, manual check. Skipping a gate is a human decision, made explicitly.

human

templates

three files, fixed shape

Every section is fixed — do not delete, reorder, or rename. One line per item, no essays, every claim checkable. Seeded from templates/ inside the skill.

◈

SPEC.md

the contract

The contract for what we build. Every acceptance criterion must be testable by a command or a human action; every risky dependency has an exact pinned version — no ^ ranges.

# SPEC: <project name>
## problem statement
## intended users
## required behavior & UX
## architecture & components
## security & privacy
## supported versions
## non-goals
## acceptance criteria
## notes

⇧

ROADMAP.md

the phases

Phases to delivery, ordered by dependency. Each phase ships as one reviewable PR, ≤3 tasks per phase, exit criteria checkable.

# ROADMAP: <project name>
## phase 1: <name>
  deliverables
  dependencies
  exit criteria
  acceptance baseline

☑

TASKS.md

the executable slice

Vertical slices — each task delivers working value on its own. Exact acceptance command plus expected output, TDD steps ticked in order, never skipped.

# TASKS: <project name>
## task T1: <title>
  phase
  files touched
  acceptance: command + expected
  tdd: red → green → refactor → commit

principles

what holds the pipeline together

Free-tier models are already pinned per agent — planning and gates on nemotron-3-ultra-free, execution on deepseek-v4-flash-free, tests on north-mini-code-free. Don't override them.

↻

reuse, not duplicate

dispatch, don't rebuild

The repo already has agents and skills for every step. Your job is to dispatch them in the right order with the right inputs — never reimplement their behavior.

▤

small phases, small PRs

token economy

One phase per execution session, never the whole roadmap. Compact handoffs — pass paths and acceptance commands, not file dumps or conversation history.

⚠

the tool is replaceable, the gates are not

the gates are the point

Any model can write code. The value lives in the gates — test scaffold first, /finish, fresh-context review, human merge check. Never weaken or skip a gate to save tokens.
